# Discussion notes — prepared answers

Short answers to the brief's 8 discussion topics, tied to this codebase.

1. **Introducing a real LLM safely** — Today it is an offline stub, not a real model. There is a `Suggester` interface in `dq/ai`, a stub behind it, and guardrails: only four fields can be sent, the response is checked strictly, and confidence is capped at 0.6. It is off by default and only runs with `--suggest`. Results are labelled `ai_assisted_candidate`, need review, and nothing is auto-applied. To go real I'd put a provider behind the same interface and start in shadow mode: the model runs, we score its output against steward decisions and the eval set, and stewards don't see it until it clears the bar. Not built yet: the provider itself, timeouts and retries, a kill switch, and cost and latency logging.
2. **Data never sent to an external AI service** — Only four fields can ever leave: description, manufacturer, category and unit of measure. A model class rejects anything else, so adding a field is a deliberate code change. Never the source system, prices, names or notes. A row is only sent if it is complete and well-formed (rows that fail the basic checks are not sent), and not if any of those fields contains an email, a web link or a phone number, which people do paste into descriptions. The record text goes into the prompt as JSON data inside a marked block, with angle brackets escaped, so it can't close the block or pose as instructions; I tested that with hostile text. This is a basic screen, not full data-loss prevention. For a vendor I'd require no training on our data, a region-pinned endpoint and a retention limit. Those are contract points; nothing in the code covers them.
3. **Validating AI output before users see it** — Two layers. First, every response goes through a strict check: unknown fields, a missing explanation, a bad confidence, or text identical to the original are rejected, confidence is capped, and any failure just means no suggestion. Second, an offline eval: 12 labelled cases, including hostile text like "ignore previous instructions", run with `python -m dq eval-suggester`. It measures accuracy and false suggestions and fails if they miss the bar, and it runs inside pytest, so it gates any change to the prompt, the model or the abbreviation list. Limits: the cases are mine, not stewards', and only the stub has been tested. A real model needs a bigger set labelled by stewards, and I haven't built a check that drops a suggestion contradicting a deterministic rule.
4. **Keeping AI-generated code from lowering quality** — I don't trust AI code by default; I make it prove itself. Spec and acceptance criteria first, tests before code, then gates it can't skip: mypy strict, ruff, a 95% coverage floor, and golden and property tests. A hook is meant to block edits to protected files like the golden output, but when I tested it I found it lets Windows absolute paths through, so it did not block my own edit of CLAUDE.md. I wrote a test that documents it and a proposed fix; a human has to apply it because the hook is a protected file. On top of that I want an independent check: a separate red-team agent, plus mutation testing, where I break the code on purpose and see if a test notices. Here it found three real bugs my own tests missed. The honest caveat: I didn't go test-first on every slice, and when the AI writes both code and tests they share blind spots.
5. **CI checks required before merge** — The same checks locally and in CI: ruff lint and format, mypy strict, and pytest with a 95% coverage floor. That run includes the golden test, the property tests (input not mutated, no banned wording, valid schema, same input gives same output) and a secret scan. Protected files (golden output, CI config, the agent policy) need the owner's review through CODEOWNERS. What I'd still close: the workflow hasn't run on GitHub yet, branch protection isn't switched on, and I'd add automated mutation testing for the rules.
6. **Deterministic rule vs AI-assisted suggestion** — I ask: would two stewards always agree, given just the data? If yes, it's a rule: a missing part number, a duplicate ID, a unit of measure that isn't on the approved list. If a simple signal usually agrees but it's a judgement, it's a heuristic with lower confidence and labelled as one: "bearing" alone is too vague, the same part number in two systems, or a keyword that says Mechanical when the category says Electrical. Only what needs language skill goes to AI, like rewriting "BRG BALL 6205" into a clear description, capped at 0.6 and only a suggestion. It's enforced, not just a convention: rules and heuristics can't import the AI package, and a test checks that each finding's source matches the layer that produced it. The boundary should move with evidence: if the audit log shows stewards always accept a heuristic, promote it to a rule.
7. **Tracking confidence, explanation, audit history** — Every finding already carries a confidence, an explanation, the evidence, the rule id and version, and where it came from (rule, heuristic or AI), with a stable id. Reviewer decisions go into an append-only audit log: who decided what, when, on which finding and which rule version. It records intent only; the records are never changed. Not there yet: model and prompt version for AI findings (there is no real model yet), and using the log to track acceptance rate per rule so we can retune thresholds. That's the next step.
8. **Guiding a team using AI coding tools** — I'd give the team the setup I used here: a checked-in manual (CLAUDE.md) with the standards, a policy that sorts files into green, amber and red by risk, slash commands for the repeated steps, and a log of what the AI was asked and what I changed. The rules for people: AI-written changes get the same review as any other, red-zone files are human-only, and risky changes get an independent red-team pass. Then measure review time, defects found after merge and surviving mutations, and turn every bug into a test. Two lessons from this build: the guard hook I relied on failed open on Windows until I tested it, so test the guardrails, not just the code; and the AI's own tests missed three bugs that the red-team found. In week one I'd start with the manual and the red-team checklist.
